# 当前展示分数的性能测量

在产品根目录使用 Node 22 和已安装的依赖，参数与命令见[英文说明](README.md)。完整测量通过机器的重任务信号量执行。
数据库地址、数据库名、代码目录和一次性容器名均显式传入；拒绝生产端口。数据库名必须以
`jobradar_test_scoreperf_` 开头，并通过环境变量指定测试配置和已解析的 DE 市场画像。

一年种子为 40000 岗位、410 天；较小种子为 3000 岗位、45 天。写入基线与迁移并发测量使用迁移前模板，
读查询的新旧实现使用同一个已迁移数据库。每个写场景复制独立数据库，分五批执行真实提交，结束后删除副本。
单次打分每批二十次，批量场景每批一次提交；占满桶的场景另外采样同时打分延迟与数据库等待事件。
结果 JSON 和执行计划写入必填参数 `--out <目录>` 指定的目录（不存在时自动创建，`run.mts` 会把它传给每一步）；只重跑 `save` 时也从这个目录读取之前的写入结果。种子均为虚构数据，不导入生产或个人资料。

## 变更日志写入开销

```sh
node --import tsx perf-seed/agent-changes-writes.mts ADMIN_URL TEMPLATE_DB CODE_ROOT LABEL --out OUT_DIR [--runs N]
```

使用 `prepare.mts` 生成的 4 万岗位模板，并迁移到 `CODE_ROOT` 对应的数据库版本。模板须无活动连接。使用空闲的临时 PostgreSQL 实例，
管理员角色需要能复制数据库、修改触发器和执行 `CHECKPOINT`。脚本使用该代码目录的默认配置和种子对应的 DE 市场。
每轮从模板单独复制数据库，`off` 禁用变更日志触发器，`on` 保持启用。`--runs` 默认每种模式三轮。

计时场景包括将 1 万岗位的分数标为过期并写入新过滤结果、通过采集入口新增和更新各 250 条岗位来源并刷新 5000 个岗位的见到时间，
以及单独刷新 1 万个岗位的心跳。公司合并和撤销移动同一批岗位，准备时给两家种子公司各补 500 个岗位。陷阱场景强制对全库跑规则扫描，
其中 1% 的样本会改写检测结果。薪资基准分别执行相同数据和一个城市的薪资变化后的重建，记录变化分组数，并按匹配的岗位分组键估算读取时涉及的岗位数。

`agent-changes-writes-LABEL.json` 记录各轮及中位数，包括各阶段的耗时、WAL 字节数和变更行数。脚本会打印汇总表。任一比较的耗时增长超过
10%、WAL 增长超过 20%，或心跳及相同数据重建产生变更行，都会以状态码 1 退出。
