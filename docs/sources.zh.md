# 来源清单：一个文件管所有采集来源

用户要的是"清楚知道有哪些来源、哪些正常、哪些异常，不要黑盒地跑"。所有采集来源现在在一个文件里：`data/config/sources.yaml`。网页 `/sources/registry` 和命令 `pnpm sources:list` 读的就是它，再加上数据库里的健康记录。

## 1. 三个副本，谁说了算

| 副本 | 是什么 | 谁改 |
|---|---|---|
| `data/config/sources.yaml` | **真相**。所有通道的开关、参数、预算，加要采集的公司 ATS board | 你、网页（设置页的"来源"标签、来源清单页）、agent |
| 数据库表 `source_registry` | 文件的**镜像**：每个条目一行；从文件里删掉的条目留着，标 `in_config = false` | runner 启动和热加载配置时、网页每次写文件后、来源清单页发现不同步时、`pnpm sources:list --sync` |
| `/sources/registry` 页面 | 文件 + 健康数据（`channels`、`runs`、`ats_boards`、`raw_postings`） | 只读视图；开关和编辑写回文件 |

网页上的所有修改都写回 `sources.yaml`（注释保留），然后立刻同步数据库。

## 2. 文件结构

```
顶部        付费总预算、熔断、并发、HTTP、"测试"按钮的规模（所有通道共用）
linkedin    LinkedIn 级联顺序和五个 LinkedIn 通道
jobspy      jobspy sidecar（linkedin-guest、indeed、jobspy-google 共用）；proxies 可能含账号密码
sources     其他通道：招聘网站、搜索 API、公司 ATS、board 发现、Gmail 提醒邮件
ats_boards  要采集的公司 ATS board：name、ats、token、enabled、可选 region
registry    来源清单页的统计窗口、判定阈值、导入大小上限、"打开 board"的地址模板
```

条目 id：通道就是通道名（`greenhouse`、`gmail-alerts`、`linkedin-session:recommended`）；公司是 `board:<ats>:<token>`（`board:greenhouse:celonis`）。

`registry:` 里的键只在 YAML 里改：`window_days`（统计窗口，7 天）、`board_failing_after`（连续失败几次算异常，2）、`board_stale_hours`（多久没检查算不稳，48）、`import_max_bytes`、`board_page_urls`，以及可选的 `candidates_page_size`（"发现的 board"一次列出几条，不写是 10；故意不写进随仓库的文件，因为写进去的默认值会被每次保存带进文件）。

默认 LinkedIn 级联为 `linkedin-brightdata` → `linkedin-apify` → `linkedin-monid` → `linkedin-session` →
`linkedin-guest`。[Monid](monid.zh.md) 使用 `MONID_API_KEY` 和独立的预充值钱包，没有 key 时跳过且不记失败。
其默认 5 美元预算受全局付费上限约束。sources 配置版本 4 只对旧默认顺序自动插入；自定义顺序和子集保持不变，
新块默认停用。自定义级联迁移后若要使用，须同时在 `/settings` 将 `linkedin-monid` 加入级联，并设置
`linkedin.monid.enabled: true`。

## 3. 七种状态怎么判

| 状态 | 意思 |
|---|---|
| 正常 | 最近运行成功；公司最近一次检查成功且不久前 |
| 不稳 | 最近有请求失败、熔断后试探中；**最近几轮的运行全是"跳过"**（级联里没有可用通道或预算用完，原因写"最近 N 轮被跳过：<原因>"，即使更早成功过）；公司最近一次失败（次数不到阈值）或太久没检查 |
| 异常 | 最近一轮失败或熔断中；公司连续失败达到 `board_failing_after` 次 |
| 停用 | 开关关了；公司所在的 ATS 通道关了 |
| 未配置 | 启用了但缺 key / 没登录（页面只写变量名，不写值） |
| 从未运行 | 通道还没有运行记录；公司还没被检查过 |
| 待命 | LinkedIn 级联里排在后面的通道：已启用、前面有可用的通道所以从没轮到（"级联备用：前面的通道可用时不会运行"）；排在"正常"后面 |

通道的状态和 `/sources` 概览页的通道卡片是同一个结果。公司按顺序取第一条：停用 → 从未运行 → 连续失败达到阈值（异常）→ 最近一次失败（不稳）→ 太久没检查（不稳）→ 正常。每一行都有一句原因，悬停看全文。

### 岗位怎样被标为可能已关闭

**最后列出**是岗位关联的所有来源原帖中最新的采集时间。链接检查不算，即使 alive 结果推进了岗位的最后看到时间。
历史库按这个来源日期排序，已关闭和休眠岗位都显示它；没有来源日期时显示未记录。

**再次出现**同样只认来源观测：新采集时间与上次列出至少间隔 `job-archive.yaml` 的 `relist.min_gap_days`
（默认 14 天），并且期间观测到过缺席，才记一次。缺席指岗位至少一个来源通道在更早的轮次中完成了一次成功运行，
未扩宽搜索窗口，开始晚于上次列出，结束早于这次观测，而且没有列出该岗位。同轮其他查询或来源不算缺席证据；
单纯通道故障后恢复不会记再次出现。记录用原帖采集时间，延迟解析也不会变成今天。
最后列出尚未记录时，来源观测只建立基线，不推测历史再次出现次数。链接检查、关注复查和用户操作都不更新最后列出或记录再次出现。
`relist.min_gap_days: 0` 关闭再次出现记录，但仍维护最后列出。
这表示本工具再次采集到，不等于雇主重新发布；首次发现和发布日期不变，手动关闭和关闭短语证据照旧受到保护。

"可能已关闭"是按时间给出的提示，不是定论，并且按通道判断，不按搜索查询判断：

可能已关闭满 `lifecycle.dormant_after_days`（默认 30 天）后，无收藏、无 `new` 到 `offer` 的申请、也无用户在招/关闭判断的岗位会休眠。
通常是连续未列出 7 + 30 天；采集故障后刚符合可能关闭条件的岗位仍会再等满 30 天。休眠不删除数据、不改状态，
只退出默认列表和自动处理（包括普通链接检查）。来源再列出或用户选择“仍在招”就会醒来，见[已关闭的岗位与历史库](usage.zh.md#已关闭的岗位与历史库)。

- 岗位连续 `possibly_closed_after_days` 天（默认 7）没有任何来源返回，**并且**它来自的每个通道在这之后都至少有一次成功运行（开始时间晚于这段天数），才会标为可能已关闭。失败、被跳过、中断或窗口比基础窗口更宽的运行不算，所以宕机的通道不会因此关闭它的岗位。
- 条数上限不变时，更宽的补窗可能被旧岗位填满。因此每次运行都变宽的通道会少标记自己的岗位，不会因补窗而多出误标；
  连续 `unseen_link_check_after_days` 天未出现的岗位，由下文的兜底链接检查接住。
- 来自公司 ATS 招聘页的岗位，还要求该招聘页在岗位超过上述天数后，被一次成功结束、没有扩大搜索窗口的运行完整读取
  （读取招聘页之后被取消或失败的运行也不算，因为它的岗位没有保存）。完整读取指读完全部列表，
  并且对开启 `fetch_details` 的 SmartRecruiters，获取每条保留岗位的详情；`fetch_details: false` 时，读完整个列表就算完整读取。
  如果没有未解决的详情，服务器回答“没有变化”也算。仍在配置中、但持续失败、返回 404、列出的岗位少于声明数量，
  或详情持续失败的招聘页，只阻止它自己的岗位被标记，直到修好或停用。
  持续 404 会在来源清单中显示异常；列表持续不足或详情持续失败时仍显示“正常”，但“最近成功”不再更新。
  从配置中移除或停用招聘页后，不再检查它，它的岗位照常随时间进入关闭判断；有一个例外：如果招聘页在岗位过期之后
  检查失败、之后才被移除或停用，这次最后的检查会一直阻止它的岗位被标记（只会少标，不会误标），只有链接检查能关闭它们。
  升级后，每个招聘页的“最近成功”为空，完整读取过一次之前，不会把它的岗位标为可能已关闭。
- 已入库的岗位只要仍在公司 ATS 招聘列表中，即使排在 `max_results` 上限之外，也算本次看到了它。
  它不会仅仅因为超出上限而被标为可能已关闭。
- 一次搜索只返回时间窗口（`window_hours`；JSearch 把它映射到其支持的窗口：今天、3 天、一周、一个月；超过一周的一律取一个月）内发布的岗位，所以某个查询没有返回某个岗位，并不说明它已下架。因此单个查询的结果本身从不会标记岗位。
- 真正的依据是随后的链接检查：它会尝试岗位的每个来源链接。任何一个链接页面仍在线，岗位恢复为有效；只有检查到的所有链接都返回 404 或 410，岗位才关闭；其他情况保持标记不变。
- 作为兜底，连续 `unseen_link_check_after_days` 天（默认 14；0 为关闭）没有任何来源返回的有效岗位，会直接检查链接，不依赖搜索覆盖或通道运行记录。这个兜底使用普通链接检查（先 HEAD，必要时再 GET，带自己的 User-Agent），不读取 robots.txt，也会检查复查未能给出答案的关注岗位，包括被 robots.txt 禁止访问页面的情况。不会先打黄色标签，只由链接决定。对同一个岗位的检查至少间隔 `unseen_link_check_interval_days` 天（默认 7），与可能已关闭的岗位共用 `max_link_checks_per_cycle` 上限。像 LinkedIn 这类要求登录或拒绝机器人的页面无法给出答案，岗位仍保持有效；需要时请手动关闭。
- 岗位被任何来源再次看到，会重新变为有效，但有两种例外：因页面写明“不再接收申请”而打上的标记会保留，你手动关闭的岗位也保持关闭。

### 公司 ATS 招聘页

对于公司 ATS 招聘页，`max_results` 是每个招聘页每轮最多入库的岗位数，
在标题预过滤之后计算。符合条件的岗位按招聘页的列表顺序取到上限为止。
超出上限但已入库的岗位，只要招聘页仍列着，就会刷新为本次已看到，
招聘页报告列表没有变化时也一样。它保存的标题和描述要等到重新进入上限范围后才更新。
超出上限且从未入库的岗位不会被新增入库。
来源清单的“保留”计数表示通过标题预过滤、且在上限范围内的岗位数。

关注公司的看板整板读取：标题预过滤保留它的全部岗位。看板的 `name` 和关注名单里的写法按公司 key 比较（忽略大小写、GmbH / Inc. 这类公司后缀和 `pipeline.yaml` 的别名），与推送用的 key 相同，所以名单里的 “Acme GmbH” 能对上叫 “Acme” 的看板。把看板的名字写得和公司一致，`/interests` 就不会再显示“没有配置招聘看板”；没有看板的关注公司只能靠目标城市的查询采到。因此关注状态变了的看板（例如名单里的某个写法现在对上了看板名），无论存着什么 ETag，都会重读一次。

已入库但被标题预过滤排除的岗位，**不算**本次看到了它。
缩小关键词范围后，如果其他来源也没有再看到它，它会照常随时间被标为可能已关闭。

SmartRecruiters 列表从第二页起，如果请求失败或返回格式有误，之前读到的岗位仍按原有的过滤、上限和详情规则保留并入库，
该招聘页记录错误。后续页返回 404 或部分响应（200 以外的成功 HTTP 响应，例如 206）也会记录，
但本身不会使运行失败；日志为 `ats board read only in part`。
如果每页都有响应，但去重后的岗位数少于声明数量，日志为 `ats board listed fewer than announced`，也不使运行失败。
这些情况下都会保留之前的验证标记，下次重新读取列表，“最近成功”不更新。

仅对 SmartRecruiters：详情请求失败不再使来源清单将该招聘页标为失败。已入库的岗位保留原有版本，并刷新为本次已看到；
新岗位暂不入库，后续轮次会重试，并排在之前详情已失败过的岗位前面；再次失败后，若服务器对已保存的验证标记返回 304，只有招聘页的列表发生变化才会重试。
不返回 304 的招聘页每轮都会完整重读，并在当轮重试。
连续失败达到 `sources.smartrecruiters.max_consecutive_detail_failures` 次（默认 3），或遇到站点级拒绝
（被拦截、登录或认证过期、限流、预算耗尽）时，本轮会跳过该招聘页剩余岗位的详情请求。
有未解决详情的招聘页不算完整读取，因此这次读取不能作为标记岗位可能已关闭的依据，但已入库岗位仍会刷新为本次已看到。
之前轮次的详情仍未解决、服务器返回 304 时也一样。

对于这些招聘页故障，只有该 ATS 本轮尝试的每个招聘页都失败、且采集到岗位时，运行才记为“中途中断”；
没有采集到岗位则记为“失败”。招聘页不存在、后续列表页请求失败或格式有误、以及详情未解决，都算招聘页失败。
仅有后续页 404、部分响应或列表数量不足不算，但同时有未解决详情时仍算失败。
只要至少一个尝试的招聘页没有这些失败，运行就正常返回已采集的岗位。
只要列表已读取、已入库岗位已刷新，即使详情失败或列出的岗位少于声明数量，来源清单仍显示“正常”；
“最近成功”只有在完整读取后才更新。

## 4. 页面上能做什么

- 看：汇总条（点一块只看这个状态）、类型 / 状态 / 搜索筛选（都在 URL 里，刷新保留）；通道按分组，公司默认异常在前。
- 开关：通道和公司的启用开关，只改文件里那一行的 `enabled`。`linkedin-session:recommended`（"为你推荐"每天读一次）要先启用 `linkedin-session`：它关着时这个开关是灰的，悬停写明原因，不会假装已启用。
- 编辑参数：通道行的"编辑参数"跳到 `/settings?tab=channels&section=<通道 id>`。
- 公司：添加、编辑、删除（删除前确认；已抓到的岗位不受影响）；"打开 board"在新窗口看招聘页。
- 发现的 board：页面下方，先列一页（默认 10 个）并写明总数，"再显示 N 个"展开更多；搜索框、ATS 和类型筛选对它同样有效，状态筛选不适用（页面会写明）。"加入"写进 `ats_boards`，"忽略"后不再出现。
- 通道详情：熔断状态、连续失败、本月用量、"立即采集"和"测试"按钮。
- 手机（窄屏）上两张表变成卡片，"详情"展开其余信息。

### 导入和导出

- 导出 YAML：文件原文（含注释），文件名 `sources-20261008-1402.yaml`。导出 JSON：校验后的值。两种都把 `jobspy.proxies` 里 URL 的账号密码换成 `***`。
- 导入：上传或粘贴 YAML / JSON，点"预览"看差异（通道启用 / 停用、参数改动、公司新增 / 删除 / 修改、其他设置），再"应用"。应用时服务器重新校验；预览之后文件被改过会拒绝，请重新预览。
- 两种方式：**整份替换**（必须是完整合法的 sources.yaml）和**只合并 ATS 公司**（文件里有 `ats_boards` 列表；新增或更新，不删除）。
- `jobspy.proxies` 永远保留当前值，导入改不了它。导出的 JSON 可以原样整份导回，没有差异。
- 先导出一份当前文件再导入，出问题可以导回去。
- 校验不通过时，错误用界面语言写明，公司用"名称（ats/token）"指出，不用列表下标；YAML 语法错误只说一次行列。
- "整份替换"删掉一家公司时，别的公司上面的分组注释留在原处；被删公司自己的分组注释移到它后面的那一家。
- `sources.yaml` 读不了时：表格显示数据库镜像（可能过期；状态较粗，只按最后一次运行判断：失败为异常，部分成功或中途中断为不稳，其余为正常），开关和编辑禁用，导出 YAML 和导入仍然可用，用导入整份替换来修复。

### 操作日志

在“来源”子导航中打开**操作日志**，也可以从命令面板进入（`/sources/logs`）；主导航不增加入口。列表可按类型、状态、时间范围筛选，也可以只看有警告或错误的条目。进行中的工作置顶，运行期间页面会自动刷新。

日志记录每次采集轮次及其七个步骤，ai-worker 执行的 ai / notify / late 步骤也归在同一轮下；还记录打分、信号复核、陷阱检测、翻译和拆解的逐岗位 AI 结果，每个来源查询（包括因预算、熔断或级联被跳过的查询），以及每次控制请求尝试。runner 和 ai-worker 的系统任务包括启动、孤儿恢复、备份、日志修剪与核对、交付条目修剪、Telegram 按钮操作和每日提醒。心跳、空轮询、配置重载、没有发送内容的提醒检查，以及保存设置等 web 进程动作不记录。

打开条目进入详情（`/sources/logs/<id>`），可看步骤树、进度和带岗位链接的逐项结果。“收到 / 没收到”表按查询显示 fetched、新增和费用；如果[付费交付账本](#付费交付账本)有对应记录，还显示送达数、计费单位、已存数和各处置结果的数量。详情页也链接到对应日期和任务的 AI 用量。

状态包括**进行中**、**成功**、**部分完成**、**失败**和带原因的**跳过**。采集结束后，**AI 排队中 / AI 处理中**表示委托的 AI 工作尚未完成。**已中断**表示工作被打断；**已中断，已重新排队**表示请求等待再次尝试。**可能已中断**表示记录仍显示运行中，但底层工作或所属进程已不再活跃；**结果未记录**表示最终结果没有被捕获。每次请求尝试保留自己的最终状态，只有最新一次尝试旁边显示请求当前状态。

**当时未记录**表示该细节没有被采集，**未知**表示数值不可用；两者都不会显示为 0。**记录不完整（丢弃 N 条）**表示丢失了 N 条日志事件。错误只显示代码和固定说明，不显示错误正文；不认识的代码显示为**其他错误**。

默认从最后一次活动起保留 30 天，同时受事件数上限约束；真正进行中的工作不会被修剪。可以删除**本条**、按**日期范围**删除或**全部清空**：每种操作都会先预览并要求确认，跳过真正进行中的工作，且只删除预览前已开始的条目。大量删除可能分几步完成，出现**部分完成，可继续**时可继续删除。删除不会改变轮次、运行、原始岗位、交付账本、AI 用量或月度预算，也不会删除备份里的数据。

在 [activity-log.yaml](configuration.zh.md#操作日志activity-logyaml) 设置 `enabled: false` 后只停止新增记录，页面显示**操作日志已关闭**；已有条目仍可查看和删除。

## 5. 命令行

```
pnpm sources:list [--type channel|ats_board] [--status failing ...] [--all] [--json] [--sync] [--strict] [--lang en|zh]
```

打印所有来源、状态和原因（表格语言跟随 `cli.locale`，可用 `--lang en|zh` 覆盖）。`--json` 输出代码值：`status`（`ok` / `degraded` / …）、`lastRunResult`（`succeeded` / `failed` / `skipped`，公司是 `ok` / `not_modified` / `error`）、`reasons`（`[{ key, values }]`）；"最近运行"和"最近成功"都是结束时间。`--status` 可重复；`--all` 带上已从文件移除的条目；`--sync` 先把文件同步进数据库；`--strict` 在有启用的来源处于"异常"时退出码为 1。连不上数据库时只列出文件里的条目（状态"未知"）。

`pnpm run doctor` 里的 `sources.registry`：有异常的启用来源或镜像落后时是 warn；`sources.yaml` 读不了时是 fail。

### 付费交付账本

默认情况下，付费通道将供应商送达的每条记录保存在本机交付账本中，包括已计费但没有成为岗位的记录。每条都有处置结果；标记补充说明。已存岗位的账本只保留哈希和原始岗位链接，不再复制原文；如果岗位后来变化，当次原文可能不再可用。账本覆盖配置范围内的真实运行；配置读不出来或表尚未就绪时，采集会继续，但没有账本记录。

| 处置结果 | 含义 |
|---|---|
| `received_uncommitted` | 已收到并写入检查点，尝试尚未结束。 |
| `unparsed_response` | 供应商响应无法读取为记录。 |
| `provider_error` | 供应商返回的错误项。 |
| `no_identity` | 记录缺少通道所需的身份标识。 |
| `duplicate_in_run` | 本次运行内的重复记录。 |
| `outside_window` | 在本地时间窗之外。 |
| `invalid_shape` | 记录无法作为岗位接受。 |
| `stored` | 已存为原始岗位。 |
| `store_failed` | 保存岗位失败。 |
| `discarded_on_failure` | 尝试失败或取消，记录未能保存为岗位。 |

| 标记 | 含义 |
|---|---|
| `unidentified` | 没有供应商标识，使用了派生标识。 |
| `date_missing` | 缺少发布日期。 |
| `date_unparsed` | 发布日期无法解析。 |
| `date_day_precision` | 日期只能精确到天。 |
| `date_unconfirmed` | 无法确认日期的精确度。 |
| `date_conflict` | 日期与相对时间不一致。 |
| `body_truncated` | 留存的响应体被截断。 |

用 `pnpm deliveries:show --run <id> [--disposition <code>] [--payload] [--json] [--lang en|zh]` 查看一次运行。可重复 `--disposition` 选择多个结果；只有加 `--payload` 才显示原文。摘要分别显示送达条数和计费单位：计费单位可能与经过本地筛选后的 fetched 岗位数不同。崩溃时，仍在传输中的响应体和检查点尚未提交的那一批可能丢失；已提交的批次保持 `received_uncommitted`。保留期见[配置](configuration.zh.md#付费交付账本delivery-audityaml)。

### 查询轮换

`collect.query_rotation` 默认为 `true`。每轮先跑在单元起始通道上从未轮到的查询，再按上次轮到的时间从早到晚排；
并列保持 `search.yaml` 顺序。在 `data/config/sources.yaml` 的 `collect` 下设为 `false` 可恢复每轮按配置顺序；
回滚到不认识这个键的旧代码前先删掉它。新增查询，或修改关键词、地点、远程范围，会产生新编号并排最前；
删除的查询不再出现。调整查询顺序只影响并列时的先后。

除“跳过且没有岗位、没有记录用量、没有花费”之外的运行都算轮到。失败、取消、未结束的运行都算，包括之后被清理为失败的孤儿运行。
花了额度或钱的预算截停，即使没有返回岗位，也算轮到，包括只付了启动费、空返回的 Apify 或 Monid 子运行。
请求前就被拒绝，以及“没有可用通道”的汇总行，都不会推进顺序。历史没有时间下限。

起始通道是选中级联里当前第一个可用通道，独立单元则是该通道本身。N 个查询的集合、起始通道不变，且每次轮到的开始时间
各不相同时，一个查询两次轮到之间，其他查询总共最多轮到 N−1 次。开始时间相同的按 `search.yaml` 顺序排，并列的查询可能
等得更久。例如，B、C、A 的开始时间相同，而配置把 A 排在前面时，A 可能再次先跑，B 两次轮到之间就隔着 C、A、A 三次。
这个公平保证只适用于起始通道；级联后续通道接剩余查询。付费通道预算用完后，guest 可以成为起始通道，改按它自己的历史排序。
一个查询都跑不了的单元不推进顺序；只有一个查询的扫描单元无需轮换。
手动运行和补跑同样推进轮换；补跑使用被替代的定时轮次的基础窗口。通道的“测试”按钮不写运行行，不影响轮换。

每个正常结束的单元输出一条 `query rotation` 日志和 `steps[collect].result.rotation` 摘要；摘要保存在该轮
`cycles.summary_json.steps` 中 `name` 为 `collect` 的条目里。它们包含起始通道（`sortChannel`）、查询数、
结果为 served/failed 的查询数（`reached`）、从未运行数、最久的已知等待及对应查询、实际请求的最大窗口（`maxWindowHours`，含补窗）；
日志还包含 `notReached`。`stretched` 统计至少有一次尝试扩大窗口的查询数；`capped` 统计补窗缺口被上限截住的查询数。
未知等待为 null。干跑按配置顺序、使用基础窗口，标记 `historyUnavailable: true`。读历史失败时警告一次并使用同样的回退。
关闭轮换时，CLI 显示 `query order: config order (collect.query_rotation is false)`；读历史失败时显示 `run history could not be read`。
没有可用起始通道本身不代表历史不可用：历史读取成功时，`historyUnavailable` 为 false，`neverRun` 为 0，最久等待为 null。
取消或抛错的单元不生成轮换摘要。

单次尝试的记录可在 PostgreSQL 的 `runs` 表中查看（也可以用 `pnpm db:studio`）：

- `usage_units`：记到通道预算上的用量，例如 JSearch 的请求数、Bright Data / Apify / Monid 的条数。同时看 `cost`：
  Apify 或 Monid 空返回的运行可能用量为零，却付了启动费。
- `window_hours`：实际向通道请求的时间窗；“没有可用通道”的汇总行是 null。
- `window_extended`：这次尝试的窗口比基础窗口更宽时为 true。

#### 来源页上的轮换状态

开启轮换时，`/sources` 显示每个关键词单元的查询数、最长等待时间（包括关键词组和地点或远程范围），以及从未运行过的查询。级联成员在级联卡片上共用一行，按当前第一个能接收查询的通道排序；如果没有可用通道，该行会说明这一点，不估算等待时间。
警告会统计等待超过补窗上限的查询数：这段缺口中的岗位可能已错过。提高预算或减少查询可以减少将来的缺口。补窗估算使用手动运行的基础窗口和整个级联家族的覆盖记录。可用性根据当前凭据、熔断冷却和大致的剩余预算判断。
这个显示是只读的：不会探测通道、改变熔断健康状态或推进轮换。`collect.query_rotation` 关闭、没有配置关键词查询或无法读取历史时，该行会隐藏。

看板发现（Tavily、Brave）使用同一个 `collect.query_rotation` 开关，在各通道内部轮换搜索。
子查询的轮到记录保存在 `runtime_state`，不在 `runs` 中，同一次运行的轮到时间相同。
它保证每条至少每 `ceil(N / 上限)` 次运行轮到一次，前提是配置和上限不变、轮换开启、每次记录都保存成功、
时钟没有回拨，而且每次都完成选中的整批，没有被预算或额度挡下、没有遇到致命错误、没有被取消；间隔未到而跳过的不算。
它不保证上面的 N−1 次。在开始写库之前发现取消时，不记轮到、不存候选、不更新运行标记；
写库开始以后才发生的取消，不撤销已经写下的东西。干跑和“测试”按钮保持配置顺序，不读写轮到记录。
详情及持续取消的影响见 [Tavily 发现](tavily.zh.md#它怎么工作)。

### 补窗

查询错过轮次或故障恢复后，补窗把回看范围延伸到它在同一家族任一通道上最后一次完整覆盖的开始时间。家族指配置里的整个级联，
独立来源则只有它自己。对补窗而言，成功、没有中断的部分成功，以及保留了岗位或花了额度、钱的预算截停，都算覆盖。
失败、取消、中断和未结束的运行不算覆盖。没有覆盖记录时，从该查询在家族里的第一次运行算起；从未运行的新查询使用基础窗口。
窗口在每次尝试前，按实际接手的通道分别计算。

两个设置都写在用户 `data/config/sources.yaml` 的 `collect:` 下，默认值如下：

```yaml
collect:
  max_catch_up_hours: 168
  catch_up_tolerance_hours: 6
```

- **容差：**`collect.catch_up_tolerance_hours` 默认 6，范围 0–72。间隔不超过“基础窗口 + 容差”时仍用基础窗口，超出的那段会丢失，
  最多丢失容差这么多小时。基础窗口为 24 小时时，周六 09:00 → 周日 09:30 的正常周末间隔是 24.5 小时，会丢大约半小时；
  整轮耗时很长或手动运行时可能丢得更多。超过容差后，窗口覆盖整个间隔，向上取整到小时，再受上限约束。
- **上限：**`collect.max_catch_up_hours` 默认 168，范围 0–720，更早的缺口不再补。上限小于基础窗口时仍取基础窗口。
  设为 `max_catch_up_hours: 0` 可关闭补窗、恢复基础窗口，无需部署；只关闭查询轮换不会关闭补窗。

LinkedIn 会话搜索、guest、JSearch 等使用时间窗的通道会补窗，只有一个查询的 Arbeitnow 扫描也一样。
**Bright Data、Apify 和 Monid 暂不自动补窗：**它们按条计费，时间档位较粗，结果也不按新到旧返回，因此始终使用基础窗口，
超出窗口的缺口会丢失；只要这次运行符合覆盖规则，仍算整个家族的覆盖，后续通道不会再补回这段缺口。
各通道只有在当前设置下能请求精确时间窗、按新到旧返回结果，并经实测确认后，才会启用自动补窗。

不使用搜索时间窗的通道也保留基础窗口，因为扩大窗口取不到更多岗位，只会让其成功运行失去“可能已关闭”的证据资格：

- 公司 ATS 招聘页：Greenhouse、Lever、Ashby、Personio、SmartRecruiters。
- 招聘页发现：Tavily、Brave。
- Gmail 职位提醒邮件。
- LinkedIn“为你推荐”。

窗口变宽仍补不回被 `max_per_group_per_location` 或通道 `max_results` 条数上限截掉的岗位。
JSearch、guest 等不按新到旧排序的通道，只返回较长时段里的一部分，最新岗位也可能不在其中。
预算在查询中途截停时，后面的关键词仍可能没搜到；补窗不会增加预算。

覆盖历史仍有三处不精确：

- Apify 后面的子运行失败时，会保留之前的结果并正常返回，这次仍被当作完整覆盖。
- JSearch 只搜每组前 `keywords_per_query` 个关键词。调整组内词序不会改变查询编号，覆盖记录可能仍指调整前的那几个关键词。
- LinkedIn 会话的每日页数单独计数，不走通道预算，也不进 `usage_units`。查询读过页面、但尚未留下任何岗位时碰到页数上限，
  会记为没有岗位、没有用量和花费的跳过，既不算轮到，也不算覆盖。

干跑和读取历史失败时使用基础窗口。单次尝试看 `runs.window_hours`、`runs.window_extended`；汇总看上文的
`rotation.stretched`、`rotation.maxWindowHours`、`rotation.capped`。
变宽的运行不作为[可能已关闭的证据](#岗位怎样被标为可能已关闭)。关闭补窗会停止新的变宽运行，但历史记录不会自行过期。
要安全回滚，请在 `markJobsPossiblyClosed` 中保留 `and not r.window_extended`；否则，一些岗位可能被标为可能已关闭，
并在下次被发现时重新打开。启动不认识这两个补窗键的代码前请删除它们；见[回滚说明](upgrade.zh.md#回滚)。

### 手动补抓

手动补抓会将一次手动运行加入队列。每个查询取请求的补抓窗口、自动补窗窗口和手动运行基础窗口三者中的最大值。
`collect.max_backfill_hours` 限制请求的窗口（默认 168 小时，范围 1–720），与 `max_catch_up_hours` 无关。
服务在入队时检查该上限，runner 在执行前再次检查；请求等待期间降低上限，可能导致该请求被拒绝。

在 `/sources` 的关键词通道或 LinkedIn 级联卡片上，选择轮换状态下方的 **Backfill…**。选择时间范围和当前通道 / 当前级联或所有通道，
查看列出的按条计费通道，然后确认。轮换状态行隐藏时也可以使用该按钮。要避免付费用量，可通过 CLI 只选择 `linkedin-guest` 等免费通道：

```bash
pnpm cycle:run --backfill 2d --channel linkedin-guest
pnpm cycle:run --backfill 36h
```

`--backfill <N>h|<N>d` 接受不超过 720 小时的正整数（一日 = 24 小时），只能与 `--kind manual` 一起使用，
不能与 `--dry-run` 同用。它只将请求加入队列，由 runner 执行。在 `/sources` 查看按钮显示的排队 / 运行状态；
从 CLI 提交后，也可在 `/settings` → 手动操作的请求队列中查看。

已有运行排队或正在运行时，补抓会被拒绝。普通的 **Collect now** 请求如果范围被排队中的补抓覆盖，可以加入该补抓。
预算规则不变：请求前检查、JSearch 的均摊预算（每查询及每日上限）、会话每日页数上限和熔断仍然适用。
被拒绝的查询记为跳过；下一轮继续轮换。更宽的窗口可能使按条计费的通道每次查询取回更多记录，增加费用。

与正常运行一样，已处理的查询会移到轮换队尾；补抓不保证处理每个查询。窗口变宽的运行不能作为标记岗位可能已下线的依据。
补抓窗口不超过基础窗口，且自动补窗没有扩大窗口时，该运行按正常运行处理。

只有关键词通道使用补抓窗口。不按关键词查询、而是读取自己的职位板或收件箱的通道（ATS 职位板、Arbeitnow 信息流、邮件提醒、Brave / Tavily 发现来源、LinkedIn 登录态推荐）
在同一次补抓运行中照常采集：窗口不放宽，它们的运行也不标记为窗口已放宽。

## 6. 常见异常怎么处理

| 看到 | 怎么办 |
|---|---|
| SmartRecruiters 详情请求失败 | 来源清单仍显示“正常”；`ats board details missing` 日志列出失败和跳过的数量。已入库岗位刷新为本次已看到；新岗位在后续轮次重试，但再次失败后，若服务器对已保存的验证标记返回 304，只有招聘页的列表发生变化才会重试；不返回 304 的招聘页每轮都会完整重读，并在当轮重试。有未解决详情（包括返回 304 时）就不算完整读取：“最近成功”不更新，这次读取不能作为标记岗位可能已关闭的依据。在运行结果判定中也算招聘页失败；只有该 ATS 本轮尝试的每个招聘页都失败、且采集到岗位时，运行才记为“中途中断”，没有采集到岗位则记为“失败”。见[公司 ATS 招聘页](#公司-ats-招聘页)。如果持续被拒绝，检查招聘页和网络，或增大 `sources.smartrecruiters.throttle` 的请求间隔 |

## Arbeitnow

Arbeitnow（`arbeitnow`）是免费公开的招聘板接口：不要 key，不用登录。它是德国包的本地渠道之一，默认 `sources.yaml` 里开着
（`markets: [DE]`）；已有的安装由配置更新（`pnpm config:migrate`）补上同样的块，标题预过滤词从它的 `greenhouse` 块复制。

- **每轮读什么。** 接口不收关键词和地点。每轮读整个招聘板最新的几页（最多 `max_pages` 页，默认 8 页，每页间隔 1 到 3 秒），
  留下本轮回看窗口内的岗位，并且和公司招聘页一样只存通过 `title_prefilter` 的标题：命中搜索关键词或 `include_terms`，或属于
  关注的公司；`exclude_terms` 去掉学生岗和实习。招聘板上约一半岗位不在德国：地点过滤会去掉不符合你市场的，同一岗位若也来自
  公司的 ATS 招聘页，会合并成一个。
- **一条岗位有什么。** 标题、公司、一个自由文本地点、远程标记、自由文本的岗位类型（作为合同提示保留）、标签和 HTML 描述
  （陷阱扫描会读其中的隐藏文字，见 [ai-traps.zh.md](ai-traps.zh.md)）。没有薪资字段（薪资从正文里读）。岗位链接指向它在
  arbeitnow.com 上的页面。
- **条款。** 接口按现状提供，可随时撤销；使用它的平台要链回 arbeitnow.com（Arbeitnow 条款第 11 节）。`/sources` 上的
  Arbeitnow 卡片带这个链接。若你把实例用于商业用途或对外展示岗位，请自行阅读 [Arbeitnow 条款](https://www.arbeitnow.com/terms)；
  不要把采集到的数据镜像或再发布（第 2.1.5 节）。
- **限制。** 各页分别缓存、页内不按日期排序，所以某一轮漏掉的岗位通常下一轮会补上。响应里的限额头也是缓存下来的，不使用。
  429 按它的 `Retry-After` 重试；403 或 410（接口被撤销）算被封，打开该通道的熔断，其他通道照常运行。
- **设置**：`sources.arbeitnow` 下的 `base_url`、`user_agent`、`max_pages`、`max_results`、`throttle` 和 `title_prefilter`
  （设置页上也有）。用 `enabled: false` 或 `/sources/registry` 上的开关关掉它。

## 抓取

并非每个通道都用官方 API。有些读取公开网页或非官方接口，有些以你自己登录的账号操作。多数招聘网站的服务条款禁止自动访问，
所以这些通道**在新安装里默认关闭**，需要你明确同意才能打开。

| 类型 | 通道 | 默认 | 风险 |
|---|---|---|---|
| 抓取 | LinkedIn 游客搜索（`linkedin-guest`）、Indeed（`indeed`）、StepStone（`stepstone`）、XING（`xing`）、经 sidecar 的 Google Jobs（`jobspy-google`） | 关 | 网站条款可能禁止；你的 IP 可能被限流或封禁 |
| 账号自动化 | LinkedIn 登录会话（`linkedin-session`、`linkedin-session:recommended`） | 关 | 使用你自己的账号；账号可能被限制或封禁 |
| 官方 API 和公开的公司数据源 | Arbeitsagentur、[Arbeitnow](#arbeitnow)、Greenhouse、Lever、Ashby、Personio、SmartRecruiters（开）；JSearch、Gmail 提醒、Tavily、Brave（需要你的 key 或账号） | 开，或填 key 之前关 | 遵守各提供方自己的条款和配额 |
| 付费抓取服务 | Bright Data、Apify、[Monid](monid.zh.md) | 开，但没有你的 token 就什么也不做 | 由服务替你抓取；**这并不能消除服务条款风险**，风险仍在你身上 |

怎么打开：

- **设置向导的"来源"步骤。** 抓取类和账号类通道永远不会被预先勾选，即使你的市场包把它们列为本地渠道。勾选时会出现说明和一个确认框，
  必须勾上才能保存这一步。用 `pnpm run setup --answers` 时设置 `sources.acknowledge_scraping: true`（见 [setup.zh.md](setup.zh.md#答案文件)）。
- **`/sources/registry`。** 打开这类通道的开关会先弹出带同样说明的对话框，确认后才写入。关闭不需要确认。服务端也会拒绝没有确认的开启请求。导入文件如果会开启这类通道，预览里会显示同样的说明，并要先勾选确认框才能应用。
- **设置页或直接改 YAML。** 在那里设置 `enabled: true` 视为你的明确决定：设置表单在开关旁显示说明，但不拦截。`/me` 上（换市场之后）的"开启它们"按钮会跳过这些通道，
  并提示你去来源页处理。

已有的安装会保持 `data/config/sources.yaml` 原样不变；只有新安装才会从这些通道关闭开始。`jobspy.linkedin_fetch_description`
（每个 LinkedIn 岗位多一次请求去读完整描述）同样默认关闭。

每条 jobspy 搜索 POST 只发送一次，超时或 HTTP 500 时也不重复。客户端停止等待后，sidecar 可能还在抓取，重发 POST 会启动另一轮完整抓取。失败仍会计入通道熔断器；共享 HTTP 重试设置不会重复这些抓取请求。

如果你打开抓取类通道：阅读每个网站的条款，保持低请求量（少量关键词、少量城市、默认的调度），不要再发布采集到的数据，
能用官方 API、公司招聘页和你自己的职位提醒邮件就优先用。使用方式由你自己负责。
